Encryption Posture

Give it a hostname and it reports how that host's encryption holds up: which TLS versions it accepts, which key exchange groups it accepts including post-quantum ones, and what its certificate chain looks like. Every answer comes from TLS handshakes made to the host on port 443, from the outside.

https://api.securityaccelerated.com{{if .Version}} {{.Version}}{{end}}

Encryption Posture

POST /v1/encryption/lookup

Submit one or more hostnames and choose exactly which lookups to run via the lookups array — there is no default set. All requested lookups run concurrently, and every lookup is available on every plan.

Request Body

FieldTypePlanDescription
hostsstring[]AllArray of hostnames (required). Each is reduced to a bare lowercase hostname before use; entries that reduce to the same hostname are deduplicated, and plan limits count the entries you submitted.
lookupsstring[]AllWhich lookups to run (required, non-empty). Names are trimmed, lowercased and deduplicated.

Valid Lookups

NamePlanDescriptionHandshakes
protocolsAllWhich of TLS 1.0, 1.1, 1.2 and 1.3 the host accepts.4
key_exchangeAllWhich key exchange groups the host accepts, which one it picks, and whether any is post-quantum.9
certificateAllThe certificate chain: algorithms and key sizes, the leaf's expiry, whether the chain is publicly trusted, and whether it covers the host.1

The encryption catalog is separate from the domain and IP catalogs, so asking for ssl here returns 400. The handshake count is how many connections one uncached lookup makes to the host.

Hosts

A host may be written as a bare name, a URL, or host:port. It is reduced to a lowercase hostname before use:

  • Scheme, credentials, port, path, query, and a trailing dot are stripped
  • The port is always 443, whatever was written
  • IP addresses are rejected — this endpoint takes hostnames only
  • A name without a dot, an empty entry, or a name over 253 characters is rejected
  • A host that resolves only to private or reserved addresses is not probed; the lookup fails with an entry in errors

All of one lookup's handshakes go to one address, chosen once after resolving the name. A host with several addresses can be configured differently on each, so every result reports the ip it was observed on.

    "hosts": ["example.com"],
    "lookups": ["protocols", "key_exchange", "certificate"]

Response Fields

Results are wrapped in a results envelope. Each element carries the normalized host, the verbatim inputs that mapped to it, one field per lookup you requested, and errors only when something failed. Match elements by host rather than by position.

ip, probed_at -- Where and When

Every lookup object carries the same three fields alongside its own:

FieldDescription
cache_hitWhether this lookup was served from cache
ipThe address the handshakes went to. One lookup always uses one address
probed_atWhen the handshakes were made (UTC). For a cached result this is earlier than your request

protocols -- TLS Versions

Each version is offered on its own, so the answer is what the host accepts, not just what it prefers. Available on all plans.

FieldDescription
versionsOne entry per version, newest first: name (TLS 1.3, TLS 1.2, TLS 1.1, TLS 1.0) and accepted
legacy_acceptedtrue when the host accepts TLS 1.0 or TLS 1.1, both deprecated by RFC 8996

SSL 3.0 and earlier are not tested.

key_exchange -- Key Exchange Groups

Each group is offered on its own, then all of them together to see which one the host picks. Available on all plans.

FieldDescription
groupsOne entry per group tested: name (the IANA name), accepted, and post_quantum
negotiatedThe group the host chose when offered all of them at once, post-quantum first. Omitted if that combined offer was refused
verdictpost_quantum if the host accepts at least one post-quantum group, otherwise classical

Groups tested, in this order: X25519MLKEM768, SecP256r1MLKEM768, SecP384r1MLKEM1024, MLKEM1024 (post-quantum), then x25519, secp256r1, secp384r1, secp521r1 (classical). groups always lists all eight.

A post_quantum verdict says the host supports post-quantum key exchange. It is not a statement about every connection: only a client that negotiates one of those groups gets session keys that hold up if today’s traffic is recorded and attacked with a quantum computer later, and a client that offers only classical groups still gets a classical exchange. negotiated shows what the host picks when offered everything. The verdict also says nothing about the certificate, which has its own algorithm_verdict and is classical for almost every host today. A host is not “quantum-safe” because this lookup passed.

certificate -- Certificate Chain

The chain the host sends to a client that accepts anything from TLS 1.0 up, so a host too old for current defaults still gets its certificate reported. Available on all plans.

FieldDescription
chainThe certificates the host sent, leaf first. Each entry has subject, issuer, not_before, not_after, key_algorithm, key_bits (omitted when the algorithm has no single size), signature_algorithm, and self_signed
sansThe hostnames the leaf covers. Omitted when it lists none
days_until_expiryWhole days until the leaf expires, as of probed_at. Negative once expired
validity_daysThe leaf's total lifetime in days
expiry_verdictvalid, expired, or not_yet_valid
algorithm_verdictpost_quantum, classical, weak, or unknown
trust_verdicttrusted or untrusted
hostname_verdictmatch or mismatch

The four verdicts

Each verdict answers one question and is judged on its own, so a certificate can fail one and pass the others.

VerdictQuestion it answers
expiry_verdictIs the leaf inside its validity dates at probed_at? There is no “expiring soon” value: what counts as soon depends on the certificate's lifetime and your renewal process, so set your own threshold on days_until_expiry.
algorithm_verdictWhat is the weakest key or signature anywhere in the chain? See the table below.
trust_verdictDoes the chain the host sent lead to a root in the public trust store? Nothing is fetched to repair a chain, so a host that leaves out an intermediate is untrusted even where a browser would recover. Judged apart from the leaf's dates: an expired certificate from a public CA is expired and trusted.
hostname_verdictDo the leaf's subject alternative names cover the host you asked about? Wildcards cover one label. The common name is not consulted.

algorithm_verdict is the weakest thing found anywhere in the chain:

ValueMeaning
weakAn RSA key under 2048 bits, an elliptic curve key under 224 bits, a DSA key, or a certificate signed with MD5 or SHA-1
unknownAn algorithm this service does not recognize
classicalSound today, breakable by a large quantum computer
post_quantumEvery key and every signature in the chain is ML-DSA

A self-signed certificate's own signature is not scored, so an old root signed with SHA-1 does not make a chain weak.

An untrusted, expired, or mismatched certificate is reported in the verdicts, not returned as an error. The lookup succeeded: it reached the host and is telling you what it found. Only a host that could not be reached, or that refused every handshake, produces an entry in errors.

errors -- Partial Failures

If individual lookups fail, they appear here. The rest of the response is still populated.

"errors": [
  { "lookup": "protocols", "message": "no such host" }
]
MessageMeaning
no such hostThe hostname does not resolve
domain resolves to a private/reserved IP addressRefused. Only public addresses are probed
connection refusedNothing is listening on port 443
i/o timeout or context deadline exceededThe connection or one of the handshakes timed out
no TLS handshake succeeded on port 443The host answered and refused every offer
invalid hostname (lookup validation)The entry is not a hostname. Appears here only when other hosts in the request were valid; a request whose only host is invalid returns 400
raw IP addresses are not accepted; provide a hostname (lookup validation)The entry is an IP address

A lookup either returns a complete answer or fails

If any one handshake times out, the whole lookup fails rather than reporting that offer as refused, and its field is absent — not null, not a partial object:

{
  "results": [
    {
      "host": "example.com",
      "inputs": ["example.com"],
      "certificate": { "cache_hit": false, "expiry_verdict": "valid", ... },
      "errors": [
        { "lookup": "key_exchange", "message": "i/o timeout" }
      ]
    }
  ]
}

Requesting n lookups does not guarantee n fields, so code that reaches straight for result.key_exchange.verdict works in testing and throws the first time a host is slow to answer. Failures are never cached — ask again and the lookup runs again. A timeout is treated as “nothing learned” on purpose: recording silence as a refusal would let one lost packet be cached as a finding about the host.

Error Handling

StatusMeaning
400 Bad RequestInvalid request body or missing hosts field — invalid request: hosts field is required and must be a non-empty array
400 Bad Requestlookups missing or empty after normalization — lookups is required, e.g. ["key_exchange", "certificate"]
400 Bad RequestUnrecognized lookup name (including domain-only names such as ssl) — the message names the offending entry
400 Bad RequestMore hosts than your plan allows — e.g. too many hosts: maximum 1 allowed for free plan
400 Bad RequestThe only host submitted is not a hostname — invalid hostname or raw IP addresses are not accepted; provide a hostname
401 UnauthorizedMissing or invalid API key
413 Content Too LargeRequest body exceeds the 1 MB limit
429 Too Many RequestsRate limit exceeded -- check the Retry-After header
500 Internal Server ErrorServer error -- contact support@securityaccelerated.com

All error responses use this format:

{
  "error": "description of the problem"
}
Partial lookup failures are different from HTTP errors. When individual lookups fail (e.g., the host does not answer on 443), the request still returns 200 OK with successful lookups populated and failures listed in the errors array.

Caching

Results are cached per lookup, per host under encryption:<host>:<lookup> — a namespace separate from domain lookups, so the same name asked about on the two endpoints never shares an entry. Each lookup object carries its own cache_hit, so one result can mix cached and freshly fetched fields.

LookupTTL
protocols12 hours
key_exchange12 hours
certificate4 hours

A cached result is an older observation

probed_at is stored with the result, so a cached answer reports when the handshakes were actually made, and days_until_expiry is counted from that moment. Recompute it from the leaf's not_after if you need it to the day.

Cache failures never fail a request

Caching is fail-open: an unreachable cache means every lookup is fetched live, an unreadable entry is treated as a miss and overwritten, and a failed write still returns the fetched result. Failed lookups are never cached — a failing lookup is retried on the next request rather than remembered.

Request Correlation

Every response carries an X-Request-ID the API generates for you. You can additionally send your own X-Client-Request-ID to tie a request to an identifier your systems already use — it is echoed back and recorded in server-side logs.

HeaderDirectionDescription
X-Client-Request-IDRequestYour correlation ID. Up to 64 characters, limited to letters, digits, hyphens, underscores, dots, and colons — enough for UUIDs and common trace IDs.
X-Client-Request-IDResponseEchoed back byte for byte when the value you sent was accepted.
X-Request-IDResponseA UUID the API generates for every request, whether or not you sent a correlation ID. Quote this when contacting support.
A correlation ID that is too long or contains other characters is ignored rather than rejected — the request succeeds normally, but nothing is echoed back. If you are relying on the header for tracing, treat a missing X-Client-Request-ID on the response as a signal that the value did not pass validation. X-Request-ID is always present — including on error responses, where correlation matters most — so it works as a fallback.
